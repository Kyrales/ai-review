# Накопление правил AI-review из ответов ревьюверов

Дата: 2026-09-13
Статус: дизайн согласован

## Контекст

AI-review уже умеет повторно анализировать ответы в GitFlic-дискуссиях в режиме
`followup`. Состояние обработки хранится в доверенных служебных маркерах с UUID
покрытых ответов. Проектные особенности передаются модели через
`ai-review/prompts/project-rules.md`.

Нужно позволить AI-review выделять из ответов назначенных главных ревьюверов
переиспользуемые знания, а затем по явному локальному запуску объединять их с
правилами проекта. Изменение файла остаётся незакоммиченным и полностью
контролируется пользователем.

Реализация затрагивает два репозитория:

- `F:\1C\Projects\RT_VT\ai_review`, ветка `feature/memory_answer` — формирование
  знаний во время `followup`;
- `sppr_gitflic` — конфигурация доверенных ревьюверов, локальный синхронизатор и
  управляемая секция `project-rules.md`.

На первом этапе поддерживается GitFlic. Конфигурация и внутренние модели не
должны препятствовать последующему подключению GitLab.

## Переносимость между 1С-проектами

Вся переиспользуемая логика находится в пакете `ai_review`: загрузка
конфигурации, provider API, проверка marker/knowledge-блоков, интерактивный выбор
MR, LLM-компиляция и безопасное обновление файла правил. Она не содержит имён
`rt-vt`, `sppr`, путей EDT source set или бизнес-терминов конкретной конфигурации.

Проект 1С подключает функцию четырьмя декларативными элементами:

1. секцией `knowledge` в `.ai-review-ones.yaml`;
2. своим `project-rules.md`;
3. подключением этого prompt-файла к режимам review;
4. тонким `Sync-AiReviewKnowledge.ps1`, который только запускает переносимую CLI
   `ai-review sync-knowledge` и не реализует GitFlic, JSON, YAML или LLM protocol.

Для переноса в другой GitFlic-проект достаточно скопировать launcher и prompt,
настроить YAML и предоставить те же environment variables. Изменения Python-кода
не требуются. Будущая поддержка GitLab добавляется новым provider adapter к тому
же repository-level protocol без изменения knowledge/compiler/rules-file слоёв.

Owner/project не дублируются в секции `knowledge`. Локальный repository identity
resolver определяет provider, host, owner и project в таком порядке: явные CLI
overrides, существующие `VCS__...` environment settings, канонический `origin`
Git remote. Для обычного `gitflic.ru` API URL имеет штатный default; для
неизвестного или self-hosted host требуется явный API URL. Неоднозначный или
неподдерживаемый remote приводит к fail closed. Token читается через существующие
environment/`.env` имена, а trusted AI identity provider adapter получает из
явной настройки либо authenticated-user endpoint. Launcher только передаёт
overrides и не реализует этот алгоритм.

## Пути prompt-файлов: репозиторий и runtime

В текущей интеграции существуют два разных пространства путей, и они не
преобразуются автоматически самой `.ai-review-ones.yaml`:

| Назначение | Путь |
|---|---|
| Исходные prompt-файлы в 1С-проекте | `<repository-root>/ai-review/prompts/` |
| Временная доверенная копия на CI host | `<runtime-root>/control/ai-review-<pipeline-id>/` |
| Read-only mount внутри review container | `/control/ai-review/` |
| Prompt-файлы, видимые процессу `ai-review` в контейнере | `/control/ai-review/prompts/` |

Корень исходных файлов сейчас задаётся не в YAML, а явно в project launcher
`tools/ai-review/run-ai-review.sh` выражением
`control_prompts_dir="$CI_PROJECT_DIR/ai-review/prompts"`, где
`CI_PROJECT_DIR` является корнем checkout проекта в GitFlic CI. Launcher копирует
`.ai-review-ones.yaml` и prompt-файлы в отдельный trusted control directory,
монтирует его в container как `/control/ai-review:readonly` и устанавливает
`AI_REVIEW_CONFIG_FILE_YAML=/control/ai-review/.ai-review-ones.yaml`.

Поэтому значения вида `/control/ai-review/prompts/project-rules.md` в секции
`prompt` — абсолютные runtime paths внутри container, а не пути Windows и не
пути относительно repository root. Сам YAML не знает, что им соответствует
`ai-review/prompts/project-rules.md` в checkout: это соответствие создаёт
launcher. Contract tests должны проверять source directory, staging, mount и все
runtime prompt paths совместно, чтобы одна сторона mapping не изменилась отдельно
от другой.

Для первого этапа `ai-review/prompts/` является стандартным project layout.
Проект, использующий этот layout, переносит launcher без изменения mapping. Если
проект размещает prompts иначе, он обязан согласованно изменить source path в
launcher и его contract tests; изменение только YAML-путей недостаточно.

Локальный `ai-review sync-knowledge` использует другое правило: значение
`knowledge.sync.rules_file` разрешается относительно каталога project-owned
`.ai-review-ones.yaml` и указывает на файл в рабочем checkout. Оно не должно
преобразовываться в `/control/...`: CI mount read-only, а синхронизатор работает
локально и изменяет project file до будущего ручного commit.

Инструкция подключения knowledge sync к любому 1С-проекту обязана отдельно
объяснять:

1. рекомендуемую структуру `.ai-review-ones.yaml` и `ai-review/prompts/`;
2. различие repository, CI-host staging и container runtime paths;
3. точное место, где launcher задаёт source-to-runtime mapping и read-only mount;
4. почему секция `prompt` содержит `/control/...`, а
   `knowledge.sync.rules_file` — относительный project path;
5. необходимость подключить `project-rules.md` ко всем используемым режимам
   review и followup;
6. какие launcher и contract tests нужно менять при нестандартном расположении;
7. проверочный запуск, подтверждающий чтение prompt-файлов в container и запись
   только локального `project-rules.md` синхронизатором.

Инструкция не должна предполагать имена `rt-vt`, `sppr`, конкретный EDT source
set или абсолютный Windows-путь исходного проекта.

## Цели

- Запоминать подтверждённые особенности проекта, исправления ложных срабатываний
  и дополнительные проверки, сообщённые доверенными ревьюверами.
- Публиковать результат первичного осмысления непосредственно в GitFlic-ответе
  AI с пометкой `#ai-review-knowledge`, без CI-артефактов.
- Синхронизировать знания только из выбранных пользователем открытых MR.
- Перед изменением `project-rules.md` выполнять отдельный LLM-анализ, устранять
  дубли, объединять близкие положения и выявлять конфликты.
- Никогда не изменять ручную часть файла и не создавать автоматические commit.

## Не входит в первый этап

- Реализация синхронизации для GitLab.
- Автоматический запуск синхронизации после pipeline.
- Автоматические commit, push или Merge Request с изменениями правил.
- Постоянная база данных, реестр уже применённых ответов или provenance-метки в
  `project-rules.md`.
- Запоминание ответов обычных, не включённых в allowlist ревьюверов.

## Термины

**Предлагаемое правило** — переиспользуемое знание, выделенное followup-моделью
из одного конкретного ответа доверенного ревьювера. Оно ещё не является правилом
проекта, пока не прошло локальную синхронизацию.

**Ручная часть** — существующий текст `project-rules.md` вне управляемой секции.

**Управляемая секция** — единственная область `project-rules.md`, которую вправе
пересобирать `Sync-AiReviewKnowledge.ps1`.

## Конфигурация доверенных ревьюверов

В `.ai-review-ones.yaml` добавляется секция:

```yaml
knowledge:
  enabled: true

  trusted_reviewers:
    gitflic:
      - "oleg"
      - "chief-reviewer"
    gitlab:
      - "oleg.gitlab"

  max_rules_per_reply: 3

  sync:
    rules_file: "ai-review/prompts/project-rules.md"
```

Настройки имеют следующую семантику:

- `enabled` — главный feature flag; значение по умолчанию `false`;
- `trusted_reviewers` — provider-specific allowlist username;
- `max_rules_per_reply` — лимит предлагаемых правил из одного ответа, целое число
  от 1 до 3, по умолчанию 3;
- `sync.rules_file` — путь к изменяемому Markdown-файлу относительно каталога
  `.ai-review-ones.yaml`, по умолчанию `ai-review/prompts/project-rules.md`.

`sync.rules_file` должен быть относительным путём без `..`, wildcard и URI,
оканчиваться на `.md` и после канонического разрешения оставаться внутри
репозитория, содержащего конфигурацию. Reparse point/symlink, выводящий target за
пределы репозитория, отклоняется. В CI followup это поле не открывается и не
монтируется на запись; оно используется только локальным синхронизатором.

Секция `knowledge` и списки отдельных провайдеров необязательны. Отсутствующая
секция равнозначна `enabled: false`. При `enabled: false` followup полностью
сохраняет прежнее поведение: knowledge-extractor не вызывается и тег
`#ai-review-knowledge` не публикуется. Локальный синхронизатор сообщает, что
функция выключена, и завершается до чтения MR, вызова LLM или изменения файла.

При загрузке username обрезаются по краям, пустые значения запрещаются, а
дубликаты после сравнения без учёта регистра устраняются детерминированно с
сохранением первого написания. `enabled: true` с отсутствующим или пустым
allowlist текущего провайдера допустим, но ни один ответ не является источником
знания.

Для идентификации используется `username`, потому что это общее доступное поле
GitFlic и GitLab. GitFlic предоставляет `id`, `username`, `fullName`; GitLab —
`id`, `username`, `name`. Отображаемое имя не уникально и для доверия не
используется. Сравнение username выполняется без учёта регистра. Значение автора
берётся только из ответа API провайдера, а не из текста комментария.

Доверие к AI-комментарию продолжает проверяться существующим строгим служебным
маркером и идентификатором AI-аккаунта. Отказ от ID относится только к allowlist
людей-ревьюверов.

## Выделение знаний во время followup

### Источники

Для определения основного вердикта followup получает всю дискуссию. Извлечение
знаний выполняется отдельным LLM-вызовом по машинному массиву
`eligible_knowledge_sources`.
В него входят только новые, ещё не покрытые ответы, автор которых входит в
`knowledge.trusted_reviewers` текущего провайдера. Каждый элемент содержит opaque
ID ответа, username и ограниченный текст ответа. Knowledge-extractor получает
исходное AI-замечание, актуальный код/diff и этот массив, но не получает тексты
остальных участников. Они доступны только первому вызову, определяющему verdict,
и не могут влиять на извлечение знания.

Знание выделяется в одном из двух случаев:

1. Ответ содержит чёткое переиспользуемое положение, применимое в других MR.
2. Ревьювер явно просит запомнить положение, например:
   `AI-ревьювер, зафиксируй в правилах: ...`.

Markdown-оформление обращения, включая `**AI-ревьювер**`, не влияет на
распознавание. Обычные сообщения (`исправил`, `согласен`), вопросы и сведения,
относящиеся только к одной строке текущего MR, знаниями не считаются. Явная
команда не позволяет записать пустое или бессодержательное правило: AI должен
попросить уточнение без тега знания.

### Типы знаний

- `false_positive` — условие, при котором аналогичное замечание создавать не
  следует;
- `correction` — правильный способ проверки или реализации;
- `new_check` — дополнительная проблема или условие, которое следует искать в
  других MR.

### Контракт LLM

Основной результат followup расширяется только вердиктом `withdrawn`:

```json
{
  "verdict": "fixed | open | clarify | withdrawn",
  "message": "Краткий ответ в дискуссию",
  "suggestion": null
}
```

Если присутствуют новые доверенные ответы, второй LLM-вызов получает только
разрешённые источники и возвращает:

```json
{
  "knowledge": [
    {
      "source_reply_id": "UUID или ID ответа провайдера",
      "source_quote": "Точный фрагмент ответа, подтверждающий правило",
      "type": "false_positive | correction | new_check",
      "rule": "Самостоятельное правило",
      "rationale": "Почему это правило необходимо"
    }
  ]
}
```

Внутренний обмен с Codex-LB использует строгий JSON и проверяемую модель данных.
Каждое предложение ссылается ровно на один элемент
`eligible_knowledge_sources`. `source_quote` должен быть непустым точным
фрагментом нормализованного текста этого ответа. Нормализация ограничена Unicode
NFC и приведением CRLF/CR к LF; остальные пробелы и Markdown сохраняются. Runner
детерминированно проверяет ID, автора и вхождение цитаты; модель не может
приписать правило соседнему доверенному или недоверенному сообщению. Это также
позволяет применить лимит отдельно к каждому ответу.

Из одного ответа доверенного ревьювера разрешено выделить не более
`knowledge.max_rules_per_reply` предлагаемых правил, при этом конфигурационный
максимум равен трём. Если полезных положений больше, модель объединяет близкие по
смыслу положения. При обработке нескольких ответов в одном запуске общий предел
равен `max_rules_per_reply × количество доверенных ответов`. Результат сверх
лимита не обрезается молча: блок знания для нарушившего лимит ответа не
публикуется, обычный followup остаётся работоспособным, а причина записывается в
диагностический журнал.

Невалидный результат knowledge-extractor не должен ломать корректные `verdict` и
`message` первого вызова. Разбор knowledge двухфазный: сначала проверяется
envelope и получается raw-массив, затем каждый элемент отдельно проходит
`model_validate`. Runner публикует обычный followup без отброшенных знаний.
Полностью невалидный основной verdict-envelope обрабатывается по существующей
политике ошибок followup.

Специальные fast path, включая автоматическое снятие замечания для игнорируемого
шаблона ограничения ролей, сохраняют прежний verdict, но не вправе обходить
извлечение знаний из новых доверенных ответов.

### Публикация

LLM не формирует теги и служебные маркеры. Runner детерминированно добавляет к
обычному AI-ответу читаемый блок:

````markdown
#ai-review-knowledge

```json
{
  "rules": [
    {
      "source_reply_id": "11111111-1111-4111-8111-111111111111",
      "source_quote": "Наличие подсистемы гарантировано",
      "type": "false_positive",
      "rule": "Не считать дефектом ...",
      "rationale": "В конфигурации гарантировано ..."
    }
  ]
}
```
````

Блок публикуется только вместе с корректным AI followup-маркером, содержащим
`covered` ID исходных ответов. Для каждого элемента `source_reply_id` должен ровно
один раз присутствовать в `covered`, существовать среди ответов текущего MR и
принадлежать разрешённому username. Неизвестные, повторяющиеся или неоднозначные
ID отбрасываются поэлементно. Сам по себе текст `#ai-review-knowledge` не является
границей доверия.

Формат блока строгий: ровно один standalone-тег, затем ровно одна пустая строка и
связанный с тегом fenced-блок `json`; другие обычные fenced-примеры в тексте
followup не мешают разбору. В корне только массив `rules`, а в элементах
только пять полей из примера. Дубли ключей, неизвестные поля и значения, превышающие лимиты,
запрещены. `source_reply_id` ограничен 256 символами, `source_quote` — 1000,
`rule` — 2000, `rationale` — 4000; общее число элементов не превышает
`max_rules_per_reply` на каждый уникальный `source_reply_id` и 150 на один
followup. Любая ошибка делает
невалидным весь блок, а не только отдельный элемент; MR остаётся доступным, только
если в нём есть другой полностью валидный блок.

До materialization JSON проходит в Python-ядре duplicate-aware разбор через
`json.loads(..., object_pairs_hook=...)`. Отклоняются точные и отличающиеся
только регистром дубли ключей, trailing data, нечисловые JSON-константы и глубина
свыше 16. Только после этой проверки допустим переход к Pydantic-модели.
PowerShell-launcher JSON не разбирает.

## Вердикты и состояние дискуссии

`withdrawn` означает, что исходное замечание AI признано некорректным и отозвано;
изменение кода не требуется. Он может сопровождаться знаниями типов
`false_positive`, `correction` или `new_check`.

Текущая функциональность не меняется:

- `fixed` по-прежнему может автоматически закрыть открытую дискуссию;
- `withdrawn` также считается основанием для закрытия после успешной публикации
  AI-ответа;
- `open` и `clarify` оставляют дискуссию открытой;
- человек может закрыть дискуссию самостоятельно.

Добавление `withdrawn` требует синхронного обновления всех читателей маркера,
включая `sppr_gitflic/tools/ai-review/AiReview.psm1`.
`ConvertFrom-AiReviewMarker` принимает `withdrawn`, а повторный resolve считает
`fixed` и `withdrawn` терминальными вердиктами. Опубликованный `withdrawn` не
может быть ошибочно классифицирован как человеческий reply или снова попасть в
pending.

Если доверенный ответ в уже закрытой дискуссии требует публикации знания:

1. Если провайдер позволяет отвечать в закрытую дискуссию, AI отвечает без
   изменения её состояния.
2. Если провайдер поддерживает reopen, AI временно открывает дискуссию, публикует
   ответ и повторно закрывает её.
3. Если reopen недоступен, создаётся continuation-дискуссия со ссылкой на
   исходную. В ней публикуется знание, после чего continuation закрывается.

В текущем GitFlic-клиенте реализован только resolve. Поэтому GitFlic использует
первый доступный вариант либо continuation fallback. Возможности реализуются как
явные capabilities провайдера, чтобы позднее GitLab мог поддержать reopen без
GitFlic-условий в followup-runner.

Provider-neutral модель расширяется полем `ReviewThreadSchema.resolved` и
capabilities `can_reply_resolved`, `can_reopen`, `reopen_thread(thread_id)` и
`create_continuation_thread(origin_thread_id, file, line,
publication_message) -> ReviewThreadSchema`. Последний метод обязан вернуть ID и
фактическое resolved-состояние созданной дискуссии; `publication_message` уже
содержит полный видимый ответ и доверенный marker. Continuation может быть inline
либо general, поэтому discovery просматривает оба вида дискуссий MR.

State machine для закрытой исходной дискуссии:

1. Runner строит `publication_key` и ищет его во всех inline/general threads.
2. Если публикация уже существует, LLM и повторный POST пропускаются; при
   незакрытой continuation повторяется только resolve.
3. При `can_reply_resolved` ответ публикуется в исходную дискуссию, которая
   остаётся закрытой.
4. При `can_reopen` выполняются reopen, повторное чтение состояния, POST и
   resolve. После любого сбоя выполняются discovery по ключу и восстановление
   исходного закрытого состояния.
5. Иначе `create_continuation_thread` атомарно создаёт новую дискуссию с полным
   publication message; после подтверждения discovery она закрывается.

Адаптер не должен заявлять capability, которую провайдер фактически не
поддерживает. Неизвестное `resolved` трактуется как отсутствие безопасной
возможности reopen и направляет выполнение в continuation fallback.

Перед публикацией и после неоднозначной ошибки POST runner повторно читает все
дискуссии MR и ищет такой `publication_key`. Множество covered исходной дискуссии
строится с учётом её собственных followup и всех continuation с совпадающим
`origin_thread_id`. Поэтому повторный запуск не создаёт новую continuation для
уже опубликованного ответа. Полученный `thread_id` используется для закрытия;
если публикация прошла, а закрытие не удалось, следующий запуск повторяет только
закрытие. Если reopen выполнен, но публикация не подтверждена, runner пытается
восстановить исходное закрытое состояние; ошибка восстановления остаётся явной
инфраструктурной ошибкой. При ошибке до обнаруживаемой публикации исходные ответы
остаются pending.

### Версия служебного маркера

Существующий marker v1 хранит только UUID GitFlic. Он продолжает читаться без
изменений. Новые followup, knowledge и continuation публикуются в единственной
канонической форме v2:

```html
<!-- ai-review:v2;kind=followup;head=<40-lower-hex>;covered=<b64url-id>[,<b64url-id>...];verdict=<fixed|open|clarify|withdrawn>;origin=<b64url-thread-id>;publication=<64-lower-hex> -->
```

Для v2 допустим только `kind=followup`; обязательны ровно поля из примера и ровно
в указанном порядке. Неизвестные, повторные, пустые или иначе упорядоченные поля
делают marker невалидным. `head` и `publication` — lowercase hex фиксированной
длины. `covered` содержит от 1 до 50 уникальных токенов, отсортированных по
нормализованному raw ID. `origin` всегда равен ID исходной finding-дискуссии — и
для обычного ответа в ней, и для continuation.

Opaque ID сначала приводится к строке, нормализуется Unicode NFC, запрещает
пустое значение и control characters, ограничивается 256 Unicode code points,
кодируется UTF-8 и затем base64url без `=` padding. Decoder обязан проверить
каноничность обратным кодированием; альтернативное представление того же ID не
принимается.

`publication` — lowercase SHA-256 следующего бинарного framing:

```text
ASCII "ai-review-publication-v2\0"
field(provider lowercase ASCII)
field(project NFC)
field(review ID NFC)
field(origin thread ID NFC)
field(head lowercase ASCII)
uint32be(covered count)
field(each covered raw ID NFC, sorted by ordinal UTF-8 bytes)
```

`field(x)` означает `uint32be(byte_length(UTF8(x))) || UTF8(x)`. Provider должен
быть известным enum, project и review ID — непустыми строками без control
characters длиной не более 512 и 256 code points соответственно. Такое framing
не допускает неоднозначности конкатенации и одинаково реализуется в Python и
PowerShell.

Кодек marker, вычисление publication key и проверка AI-автора выносятся из
GitFlic-specific runner в provider-neutral слой; Python и PowerShell используют
общие golden vectors. Конкретный адаптер поставляет provider/project/review ID,
trusted AI identity и capabilities.

Production entrypoint сохраняет существующий host-level lock на один MR. Runner
дополнительно перечитывает дискуссии непосредственно перед POST и подавляет уже
существующий `publication_key`. Это даёт at-most-once на текущем единственном
runner host. При добавлении второго host требуется распределённый lock; без него
остаётся узкая гонка двух одновременных POST. Синхронизатор в любом случае
дедуплицирует блоки по `provider + project + MR + source_reply_id` в памяти одного
запуска.

## Локальная синхронизация

### Запуск и выбор MR

В `ai_review` добавляется переносимая команда `ai-review sync-knowledge`. В
интеграционном проекте создаётся `tools/ai-review/Sync-AiReviewKnowledge.ps1` —
тонкий launcher этой команды. По интерфейсу он похож на `Start-AiReview.ps1`, но
решает другую задачу. Launcher передаёт путь конфигурации, аргументы
`-MergeRequestId`, `-All`, `-Yes` и необязательные connection overrides;
определение repository identity, получение MR, интерактивный выбор и изменение
правил выполняет Python-команда.

Скрипт получает только открытые MR и показывает только те из них, где уже есть
хотя бы один валидный AI-followup-ответ с `#ai-review-knowledge`. Текущий режим
диспетчера (`initial`, `followup` или `none`) на попадание в список не влияет.

Пример таблицы:

```text
MR    Ветка                 Блоков знаний    Предлагаемых правил
#52   fix/calculation       2                3
#49   feature/access       1                1
```

Интерактивный ввод поддерживает:

- один номер MR;
- номера через запятую;
- `all` или `все` — все показанные MR;
- Enter — выход.

Также поддерживаются параметры `-MergeRequestId` и `-All`. Выбрать MR, которого
нет в показанном списке, нельзя. Перед LLM-вызовом выбранные MR и их дискуссии
читаются повторно.

### Проверка входных знаний

Синхронизатор принимает блок, только если одновременно выполнены условия:

- MR открыт;
- комментарий опубликован доверенным AI-аккаунтом;
- комментарий содержит корректный followup-маркер;
- тег `#ai-review-knowledge` и ограниченный блок имеют ожидаемый формат;
- `covered` маркера содержит исходный ответ;
- автор исходного ответа входит в allowlist текущего провайдера.
- `source_reply_id` однозначно находится ровно один раз среди replies MR, а
  непустая `source_quote` после NFC и нормализации переводов строк является точной
  подстрокой текущего нормализованного body этого ответа.

Теги из человеческих сообщений, цитат, повреждённых маркеров и ответов другого
AI-аккаунта игнорируются. Если хотя бы один элемент блока не проходит эти
проверки, весь блок отклоняется атомарно.

Настройки `knowledge` читает общий Pydantic/PyYAML config layer пакета
`ai_review`. Duplicate-aware SafeLoader отклоняет повторные и отличающиеся только
регистром keys до materialization. Внутри `knowledge` разрешены только поля из
приведённого примера: bool для `enabled`, целое число для
`max_rules_per_reply`, строка для `sync.rules_file`, уникальные provider keys и
списки строковых username. SafeLoader поддерживает безопасные штатные YAML-
конструкции: aliases, anchors, merge keys, inline collections и стандартные scalar
tags. Повторные/case-variant keys, unsafe custom tags, неизвестные поля и
нестроковые элементы в trust-boundary секции приводят к fail closed.
Отсутствующая секция означает `enabled: false`. Тот же config loader используется
followup и sync CLI, поэтому проект не получает второй YAML parser.

Отдельный журнал применённых ID не ведётся. При каждом запуске все знания из
выбранных MR заново сопоставляются с текущим файлом. Модель обязана распознавать
уже учтённые знания как `duplicate`, но это best-effort семантическая проверка, а
не строгая идемпотентность. Вручную удалённое правило может быть предложено снова.

### Управляемая секция

В файле, заданном `knowledge.sync.rules_file`, создаётся область:

```markdown
## Автоматически накопленные правила

<!-- ai-review-knowledge:start -->

<!-- ai-review-knowledge:end -->
```

Синхронизатор вправе заменять только содержимое между маркерами. Поддерживается
только strict UTF-8 с BOM или без BOM; невалидный UTF-8 и другие кодировки
отклоняются. Ручные prefix/suffix хранятся и переносятся как исходные byte slices,
поэтому сохраняются побайтно. Новая секция кодируется тем же вариантом BOM и
доминирующим видом перевода строк; смешанные EOL в ручных slices не
нормализуются. При первом запуске отсутствующая секция аккуратно добавляется в
конец. В самой секции не сохраняются MR, username, reply ID, хеши или другие
provenance-метки. Пользователь может свободно редактировать результат.

В файле допустима ровно одна пара marker в правильном порядке. Вложенные,
повторяющиеся или непарные marker приводят к fail closed. Управляемая секция —
Markdown-список, где каждый элемент верхнего уровня является одним правилом.
Перед синхронизацией существующая секция разбирается в индексированный список;
если ручное редактирование нарушило эту грамматику, скрипт не обращается к LLM и
просит исправить секцию.

### Второй LLM-вызов

Модель получает:

- ручную часть правил как read-only контекст;
- текущую управляемую секцию;
- все предлагаемые правила выбранных MR.

Модель должна классифицировать каждое предложение как:

- `add` — добавить новое правило;
- `merge` — объединить с существующим правилом управляемой секции;
- `duplicate` — уже полностью учтено;
- `conflict` — противоречит ручному правилу, существующему накопленному правилу
  или другому новому предложению;
- `reject` — непереиспользуемо, бессодержательно или не относится к правилам
  ревью.

Модель получает индексированный список существующих накопленных правил и
индексированный список новых предложений. Внутренний ответ Codex-LB имеет
строгую JSON-схему:

```json
{
  "decisions": [
    {
      "source_input_indexes": [0],
      "action": "add | merge | duplicate | conflict | reject",
      "target_managed_index": null,
      "result_rule": "Итоговая формулировка одного правила или null",
      "related_indexes": [],
      "reason": "Причина решения"
    }
  ]
}
```

Модель не возвращает свободный Markdown секции и не формирует отдельный массив
операций. Каждый input покрывается ровно одним `source_input_indexes`; близкие
входы можно объединить одним решением. `result_rule` обязателен только для `add`
и `merge`. `merge` ссылается на существующий индекс, причём один target разрешено
заменять только один раз. Все индексы проверяются на диапазон и уникальность.
Скрипт локально и детерминированно выводит из валидированных решений операции
`add` и `replace`.

`result_rule` — одна непустая NFC-нормализованная plain-text строка длиной не
более 2000 code points. Запрещены CR/LF, C0/C1 control characters, HTML comments,
последовательности fenced code block, подстрока `#ai-review-knowledge` и начальный
Markdown list marker. Renderer сам добавляет `- ` и перевод строки. После сборки
целевой документ повторно разбирается: должна сохраниться ровно одна правильная
пара marker, валидный список правил и побайтовое равенство обоих ручных byte
slices.

Конфликт с ручным или существующим накопленным правилом исключает новое
предложение. При конфликте двух новых предложений связь через общие
`source_input_indexes` или `related_indexes` симметрична, и оба предложения
исключаются. Порядок входов не даёт приоритета ни одному из них.

Финальный Markdown собирается скриптом детерминированно. Неизменённые правила и
их порядок сохраняются дословно, `replace` остаётся на позиции заменяемого
правила, а `add` добавляется в порядке минимального source input index.
Конфликтующие элементы не мешают применению остальных изменений. Модель не
получает права возвращать весь `project-rules.md` или служебные marker.

Поскольку по решению пользователя не хранится реестр применённых source ID и
каждый запуск заново обращается к LLM, гарантируется только best-effort
семантическая идемпотентность. Повторный запуск может предложить другую
формулировку; поэтому diff показывается всегда, включая `-Yes`. Побайтовая
стабильность гарантируется только для детерминированной сборки уже полученного и
валидированного набора operations, но не между независимыми LLM-вызовами.

Настройки LLM читаются из environment, затем из локального `.env`:

- `AI_REVIEW_API_URL`;
- `AI_REVIEW_API_TOKEN`;
- `AI_REVIEW_MODEL`;
- `AI_REVIEW_REASONING_EFFORT`.

Секреты не выводятся в консоль и не записываются в промежуточные файлы.

Команда `ai-review sync-knowledge` использует существующий Python-клиент
`ai_review.clients.openai.v2`, не реализуя Responses protocol повторно в
PowerShell. HTTP-вызов выполняет `POST {AI_REVIEW_API_URL без завершающего
слеша}/responses`, `Authorization: Bearer <token>`, `Content-Type:
application/json`. Request содержит `model`, массив `input`, `stream: false`,
`reasoning.effort`, `instructions` и `max_output_tokens`. Как и существующий
OpenAI v2 client, parser принимает обычный JSON response либо SSE. Для SSE
обязательны ровно один `response.completed`, отсутствие
`response.failed/response.incomplete` и согласованность
`response.output_text.delta`, `response.output_text.done` и финального текста;
действуют лимиты 20 MiB и 100 000 events. Полученный текст assistant затем
проверяется описанной выше JSON-схемой. Таймаут — 45 минут. Sync-команда не
делает дополнительный retry поверх политики существующего клиента: при
окончательном transport error, HTTP не 2xx, таймауте или неоднозначном ответе
пользователь может безопасно повторить команду.

### Preview и запись

До записи скрипт показывает:

- решения `add/merge/duplicate/conflict/reject` и их объяснения;
- отдельный список конфликтов;
- полный diff управляемой секции;
- итоговое количество добавленных, объединённых, пропущенных и конфликтующих
  предложений.

Затем запрашивается подтверждение `[y/N]`. Параметр `-Yes` пропускает вопрос, но
не скрывает diff. Запись выполняется через временный файл в том же каталоге и
атомарную замену. Перед созданием временного файла процесс повторно читает
исходный файл и сравнивает его SHA-256 с хешем preview. Если файл изменился во
время LLM-вызова или просмотра diff, операция отменяется. Отдельный mutex и
`fsync` не нужны для локально запускаемой команды: внешние редакторы такую
блокировку всё равно не соблюдают, а файл остаётся под контролем Git.

## Ошибки и безопасность

- Ошибка получения списка MR не изменяет локальные файлы.
- Ошибка отдельного MR отображается в таблице/отчёте и не маскируется как
  отсутствие знаний.
- Невалидный ввод не вызывает частичной обработки.
- Ошибка GitFlic, Codex-LB, разбора JSON или локальной валидации отменяет запись
  целиком.
- Ответ LLM отклоняется, если пропускает или повторно покрывает входные индексы,
  ссылается на неизвестные индексы, возвращает запрещённый `result_rule` или
  имеет неизвестные действия.
- Текст от ревьювера и AI считается недоверенным содержимым, а не инструкцией для
  синхронизатора. Он передаётся модели только внутри явно обозначенного блока
  данных.
- Конфликты не разрешаются автоматически.
- Скрипт не выполняет commit, push, изменение дискуссий или запуск pipeline.

## Проверки

### Followup

- доверенный и недоверенный username;
- сравнение username без учёта регистра;
- отсутствие правила в обычном ответе;
- автоматическое выделение `false_positive`, `correction`, `new_check`;
- явная команда запоминания с обычным и Markdown-оформлением;
- отсутствующая секция и `enabled: false` не вызывают knowledge-extractor;
- `enabled: true` с пустым allowlist сохраняет обычный followup без знаний;
- `max_rules_per_reply` принимает только значения 1–3;
- пустая явная команда приводит к уточнению без тега;
- не более трёх правил из каждого отдельного ответа;
- несколько доверенных ответов в одном followup;
- смешанная дискуссия с доверенными и недоверенными авторами;
- знание проверяется по точной цитате только из `eligible_knowledge_sources`;
- невалидное знание не ломает обычный followup;
- корректное оформление и повторный разбор блока;
- exact и case-variant duplicate JSON keys отклоняются до materialization;
- fast path игнорируемого шаблона не пропускает extraction;
- `withdrawn` и отсутствие регрессии `fixed/open/clarify`;
- `withdrawn` не превращается в pending при чтении PowerShell-диспетчером;
- ответ в закрытой дискуссии, reopen и continuation fallback;
- provider capabilities и `resolved` корректно выбирают ветку state machine;
- повторный запуск находит continuation по publication key и не дублирует её;
- marker v1 читается, marker v2 поддерживает opaque provider ID;
- параллельные запуски под production lock публикуют один knowledge-ответ;
- ответ, появившийся во время LLM-вызова, остаётся pending.

### Синхронизация

- один и тот же Python core работает для двух GitFlic fixtures с разными
  owner/project, rules path и расположением launcher без изменения кода;
- provider-neutral fake GitLab adapter проходит knowledge/sync contract без
  ветвлений по GitLab внутри domain и orchestrator;
- переносимые модули не содержат `rt-vt`, `sppr` и путей EDT source set;
- отображаются только открытые MR с валидным тегированным AI-followup;
- текущий режим диспетчера не влияет на список;
- выбор одного MR, списка, `all`/`все`, Enter и невалидный ввод;
- повторная проверка состояния перед LLM;
- поддельный тег, неверный AI-автор, повреждённый marker и недоверенный источник;
- неизвестный/повторяющийся `source_reply_id` и несовпадающая `source_quote`;
- allowlist parser: реальный YAML, quoted username, отсутствующая секция,
  `enabled`, лимит, `sync.rules_file`, безопасные standard YAML constructs,
  запрещённые custom tags и повторные provider keys;
- выключенная функция завершает sync до GitFlic/LLM и записи;
- абсолютный/выходящий за репозиторий/symlink-target `rules_file` отклоняется;
- ноль, одна или несколько пар marker управляемой секции;
- `add`, `merge`, `duplicate`, `conflict`, `reject`;
- конфликт не блокирует независимые изменения;
- конфликт new-vs-new симметрично исключает оба входа;
- decision не может добавить правило без проверенного источника;
- `result_rule` с переводом строки, list marker, control character, fence или
  managed marker отклоняется;
- полный diff до подтверждения;
- отказ `[N]` не меняет файл;
- `-Yes` пропускает вопрос, но показывает diff;
- два последовательных запуска с различными допустимыми LLM-ответами всегда
  показывают новый diff и не обещают побайтовую стабильность;
- сохранение ручной части, BOM и переводов строк;
- UTF-8 с/без BOM, CRLF/LF, смешанные EOL в manual slices и invalid UTF-8;
- конкурентное локальное изменение файла отменяет запись;
- ошибка API, LLM или JSON не оставляет частично записанный файл;
- токены отсутствуют в выводе и временных данных.

## Критерии готовности

- Followup публикует `#ai-review-knowledge` только для переиспользуемых знаний из
  новых ответов разрешённых ревьюверов.
- При `knowledge.enabled: false` дополнительный LLM-вызов и синхронизация
  отсутствуют.
- Из одного ответа выделяется не более настроенного числа предлагаемых правил
  от 1 до 3; лимит не является общим лимитом MR или запуска.
- `withdrawn` корректно отзывает ложное замечание без требования менять код.
- Существующая обработка и автоматическое закрытие `fixed` не нарушены.
- Синхронизатор показывает только открытые MR с уже опубликованными знаниями и
  поддерживает выбор всех показанных MR.
- Отдельный LLM-вызов изменяет только управляемую секцию, не добавляет конфликты и
  выдаёт валидированный JSON.
- Пользователь видит полный diff и подтверждает запись.
- При успехе скрипт создаёт или изменяет только
  `ai-review/prompts/project-rules.md`; существующие изменения пользователя в
  worktree не затрагиваются.
- Для другого 1С-проекта с GitFlic достаточно добавить секцию `knowledge`, файл
  правил и тонкий launcher; изменение или копирование Python implementation не
  требуется.
- Provider-specific код изолирован adapter-ами; добавление GitLab не требует
  менять knowledge extractor, compiler, managed-section writer или выбор MR.
